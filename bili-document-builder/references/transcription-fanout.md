# 并行转写契约

「读画面、写内容」是整条链路里唯一能并行的环节。其余阶段（采集、去重、立知识树、立页清单、
合并、校验）由主代理串行完成。

## 为什么只有这一步能并行

转写只是读图、写文件，不占本地模型内存，可以随便开几条。上游的音频识别不行：
本机模型要占显存和内存，同时跑多路会卡死，那条链路保持逐个分集串行
（见 [bili-2-ppt/SKILL.md](../../SKILL.md)）。
两条链路的要求不同，不要互相套用。

## 通用协议

### 一、主代理先立清单

并行之前必须先有清单，否则各批各写各的，拼起来顺序和口径都会乱。

- 知识树 `notes.plan.json` 由 [bili-knowledge-tree](../../bili-knowledge-tree/SKILL.md) 产出；
- 页清单 `pages.plan.json` 由本技能的主代理读知识树与画面材料后产出。

清单都是**中间产物**，放在系统临时目录下的 `$WORK/plan/`，可以带画面文件与时间；交付物不可以。
片段写到 `$WORK/fragments/`，**不写进仓库或交付目录**。

切批规则：

- 批数取用户指定的数字，没指定就用 **5**；
- 按知识边界对齐，不把一个知识点切进两批；
- 单元数少于批数时按实际单元数开，不硬凑空批。

### 二、派发

每个子代理的输入一次性给全，子代理不再回头问：

- 本批的清单片段（页号、要点、依据的画面、缺失项、每页的容量评估与是否在复查列表）；
- 这批单元对应的画面文件路径，以及字幕阶段的纠错稿 `*.corrected.json` 与 `glossary.json`
  （只给纠错稿，不给原字幕）；
- 要遵守的规范文件：`narration-refine.md`（口语稿怎么纠错、去口语、按逻辑重排）
  加上本批要产出的每种形态的模版——Markdown 模版给 `templates/<模版名>/` 下的
  `描述.md` 与 `案例.md` 两份，deck 给 `deck-design.md`；
- deck 批次另给本份 deck 的样式表 `deck_style.py`（主代理读模版原件后写好）与模版原件路径；
- mermaid 的主题、配色和收尾纪律在 `$SKILL_ROOT/references/mermaid-style.md`，
  凡是画图的批次都要一并给子代理——所有模版都指向这一份，不给它会各写各的配色；
- 输出路径和文件格式。

### 三、产物

每一批按所选交付物各写一份：

- `fragments/pg03-pg07.deck.py`：一个 `build(prs, kit, style)` 函数，按页清单逐页构图，
  把本批的页加到 `prs` 上。每页用 `style` 里的页面外壳（背景、版头、版脚）开页，
  内容区用 `kit` 的绘图工具按这一页的内容自由排，取值一律来自 `style`。不要自己 `save`。
  **画面是页面的主体**：优先用 `kit.picture()` 把真实画面装进模版的相框做法里（配一段说明
  这画面证明了什么），只有需要一眼看清的代码与表格才用原生元素重建；
  同一文件再给一个 `build_vector(prs, kit, style)`：页序、标题、文字与 `build` 一致，
  每一处画面改用原生矢量元素重绘，供图形版使用；
- `fragments/pg03-pg07.<模版名>.md`：每个所选 Markdown 模版一份片段，
  如 `pg03-pg07.知识博客文章.md`、`pg03-pg07.八股模拟面试.md`。

**批的粒度按分类切，不按页数均分。** 一个分类通常 14–30 页，
切批时不要把同一个分类切进两批——各批独立写出来的东西接不上。
一集的时长只用来估这个分类该有多少页，不用来决定批的大小。

各份片段必须来自同一棵树：术语、分类、结论一致。**不允许各自独立取材**，
否则同一份材料出来的几份文档会互相对不上。

### 四、子代理禁止

- **纠错别字、复查字幕**：纠错稿已是定稿，术语照 `glossary.json` 写，`[?]` 写成「待补充」；
- **裁剪截图**：画面只用 `kit.picture()` 整幅等比放入，不用 PIL 预裁、不设 `crop_*`、不拉伸；
- **把超载的页硬塞进一页**：页清单标了高风险的页按清单拆好的结果做；临界页先用
  `kit.text_height()` 量再定框，放不下就在 `missing` 里报告，不要缩到正文字号下限以下；
- **自行出图自检**：两层校验（`validate_deck.py` 全量 + 定向看图）由主代理在合并、注入动画后统一做；

- 改单元顺序、改标题口径；
- 改 `deck_style.py`，或在片段里另写样式表之外的颜色、字体、字号；
- 引入任何外部库；
- 跨批引用（片段里的标识只能用自己的单元区间）；
- 补写没有依据的内容——材料里缺就写进 `missing`，不要编。

## 合并

**先确认所有批次都已回报完成，再动手合并。** 子代理写完文件不等于收工——
它可能还在自检、补漏、改排版，之后会再写一次。片段在合并之后被改写，
合出来的成品就是旧版本，且没有报错。

合并前后各查一次：

- 合并前：确认每批都汇报了完成；
- 合并后：**比对成品与各片段的修改时间，成品必须比所有片段都新。**

发现片段更新了就重新合并，并重跑校验。这一条是硬的——
「文件落盘」和「这批做完了」是两件事。

主代理按顺序拼接，然后做四件事：

- **补承接**：每一节开头加一句承接上一节的过渡，批次交界处重点检查，
  各批独立写出来的东西天然像并列的卡片；
- **补引入**：检查跨批的语义是否断裂，术语口径是否一致；
- **去重**：跨批再查一次，讲同一件事的两处合并，保留双方内容；
- **成文**：用 `normalize_md.py --template` 规范排版，跑校验脚本（注意：结尾不写复习清单/自测清单）。

deck 的合并不是拼字符串，是把各批的 `build` 按页序调用一遍：

```python
import importlib.util
import deck_kit as kit
import deck_style as style

prs = kit.new_deck(title=主题, template=style.TEMPLATE)
for path in sorted(fragment_paths):        # pg03-pg07.deck.py 按名排序即页序
    spec = importlib.util.spec_from_file_location(path.stem, path)
    module = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(module)
    module.build(prs, kit, style)
kit.save(prs, f"{主题}-学习笔记PPT-图片版.pptx", heading_font=style.FONTS["heading"],
         body_font=style.FONTS["body"])
# 图形版：同样的循环改调 module.build_vector，存成 f"{主题}-学习笔记PPT-图形版.pptx"
```

合并完再跑 `inject_animations.py`——动画注入是最后一步，不在分批里做。

## 失败处理

某个子代理失败或产出不合规范时，只重试该批次，不整体重跑。其余批次的结果保留。
